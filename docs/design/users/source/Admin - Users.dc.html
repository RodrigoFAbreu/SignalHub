1Users: the list and the detail

Shell A, one version. One row per user: name, role tag, and the counts the operator scans (devices, producers, subscriptions) plus when they were last active. The management API has no per-user last-active time; the page takes the newest of the user's devices (all already in the device list), so no server change is needed. The pane is the user's whole story in the order of the operator's tasks: who they are and their role (a Basic, Mod or Admin choice with what each means), their devices (with a way to connect another), their producers, their subscriptions (with Subscribe and Unsubscribe), and their recent traffic, with a link to Events filtered by that user. Revoking sits at the bottom with its consequence in words. Invite a user is a tonal header button. Invite a user, role changes, unsubscribing and revoking are in-page dialogs (Admin - Users dialogs.dc.html). Sample data only.

Columns: User (avatar, name and a tag for a state worth noticing: No device yet, Revoked), Role (Admin filled, Mod grey, Basic outlined: a word, never red), Devices (active only), Producers (owned), Subscribed, Last active. There is no sort control: the page orders the list itself, by name, revoked users last. Filters: All, one chip per role, Revoked, and No device yet (an invited user nobody has connected a device for); the chips wrap onto a second line when the pane is narrow. A pane section never shows more than its content needs; the traffic and the revoke action are below, see U2. The role segment opens a confirmation when a different role is chosen (never changes on tap alone).

Accessible names. Landmarks: the rail is a navigation named “Sections”, the list and pane are the main region. Headings: “Users” is the level 1 heading; the open pane's title is level 2 and its sections (Role, Devices, Producers, Subscriptions, Recent traffic) are level 3. Each repeated action names its object: “Rename Ana”, “Connect a device for Ana”, “Unsubscribe Ana from ci-pipeline”, “Revoke Ana”. The role choice is a radio group named “Role of Ana”. Icon buttons have names (“Refresh the user list”, “Close the detail”).

Traffic loads when the section first scrolls into view or the user is opened, with the progress bar of the states turn. Each event row opens that event in Events (the address changes); “Open in Events” opens the Events section filtered by this user. The Pushes tab (second half of this frame, shown for example) says in words what happened to each device: delivered, not sent because pushes are paused on that device or filtered out by its push preferences, not sent because it has no push address, push address rejected and removed, waiting for a retry (only while tries remain), or gave up after 5 tries. The tab labels read “newest 20” because that is all the server returns; a user with fewer shows the real count.

For an admin the role sentence says where the role is changed. The server has no last-admin guard: revoking an admin user revokes them and makes them Basic, and a role change away from Admin simply happens. When the change would leave nobody an admin, the confirmation warns first (“Nobody will be an admin in the app. The admin token still works here.”) and then goes ahead; the operator's admin token is the way back. A revoked user's pane has no role control or actions, a grey banner (“Revoked 12 Sep. Their devices are revoked and their producers disabled. Their events stay.”) and the same sections read-only. Their name stays taken: names are unique ignoring case, revoked users included.

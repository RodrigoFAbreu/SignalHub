5Gaps in the API proposal, for the admin page

Found while drawing. Six are now settled in the API proposal; one is left to the owner at G8. Numbered, as the notes above refer to them.

GSeven gaps: six settled, one open

1. Settled. The answer object carries via (APP or WEB): the pane's “in the app / on the web page” line.
2. Settled. The answer carries by.id and by.name, the name as it was when the answer was given.
3. Accepted. “Rodrigo or Ana can answer” may name someone who has since unsubscribed; the admin page does not see subscriptions either.
4. No server change. A revoked answerer is found by matching by.id against the Users list the page already loads; if the user is not there, only the name shows.
5. Open, for the owner at G8. An answerState filter (OPEN, ANSWERED, CLOSED, NONE) on the admin events list for the Answer state chip. toAnswer=true is always empty for the admin token. The markers need no server change.
6. Settled. Choice ids are derived by one rule (lower case, accents removed, runs of other characters become “-”, trimmed, “choice-N” when nothing is left, “-2”, “-3” on a collision), written in the proposal so the SDK, the command and the dialog agree.
7. Settled. The admin test endpoint uses the producers' validation, and its errors name the field (ask.closesAt and so on), so the dialog shows them on the field with the texts of D1b and D1g.

SignalHub design system

The look SignalHub already has, written down so new screens extend it instead of replacing it. Material 3, generated from Flutter's indigo seed, dark first (the app follows the phone's light or dark mode), Roboto, Material Symbols. Every value here is taken from the running app and its theme code, not invented. Each component below lists its accessible names, and a short Accessibility section covers text size, focus and motion. The patterns added for users (bottom navigation, the producer row, search and filter chips, role sections, the key shown once, the empty state, and the QR sign-in card) come next, then the feedback and state components the new screens share (snackbar, dialog, field error, banners, loading, the bell, tags, the key box, the badge, the “not available” screen, the What's new card) with the rule for undo or confirm. The app builds them in R65, the web page in R66, from this page alone.

How new screens are decided

1. Precedence

The owner's words, then this design system, then Material 3 (app) or the Web Interface Guidelines (web page), then any design skill's defaults. No tool changes the palette, type or patterns on its own.

2. Extend, don't restyle

A new screen reuses the components below. A new component is added here first, built from the same tokens.

3. Restraint

Product screens are for operating, not persuading: at most one expressive element per screen, and only where this page allows it.

4. Touch and type

Touch targets are 48 dp. Text uses the Material type scale below; no sizes picked per screen.

5. Summaries

Folded groups and list rows sum up their values in one line joined with middle dots (Info · Normal · producer). It is SignalHub's own pattern and stays.

6. Generic by design

Nothing looks different per producer: style depends only on an event's category and severity.

7. Words

Plain sentences that say what happened and what to do, never blaming the person. The server's operator is “the host”: never name a person as the server's admin.

Text size and long names

Scale

Type follows the system text size up to 200% (Flutter's text scaler), except the bottom bar's labels, which are capped at about 1.3x. Rows grow in height and never clip.

Names

A one-line name ends in an ellipsis while its tag (Yours, Admin), the bell and the chevron keep their size. At 200% a row's summary wraps to two lines; the name still truncates at its end.

Bar, dialogs, buttons

Bottom-bar labels never wrap: their text scale is capped at about 1.3x, and the icons and the pill keep their size, so the bar grows only by the extra line height. Dialogs and sheets scroll. Buttons grow and their labels wrap. Keys and addresses wrap at any character.

Focus order and visible focus (web page)

Order

Focus follows reading order: rail, header, then the content; on the sign-in page Use a code instead comes before the QR code. A dialog starts on Cancel and keeps focus inside until it closes; Escape closes it (and a menu) and returns focus to the control that opened it.

Ring

A visible focus ring on every control: 2 px primary, 2 px offset, never removed. Rows, chips and buttons use it; the state layers below apply on top.

Undo or confirm

If an action can be reversed exactly and only the person who did it is affected, do it at once and offer Undo in a snackbar. If it cannot be reversed, or someone else is affected, ask first in a confirmation dialog. If it is harmless and reversible by the same control, do nothing extra.

Patterns to keep

PatternRule
NavigationA bottom navigation bar with three destinations (Inbox, Producers, Settings), four for an admin (People added), the unread count as a badge on Inbox. Settings is a tab: the inbox app bar has no gear. Screens pushed from a tab hide the bar and show a back arrow. On the web page the bar is a navigation rail beside a wide screen.
Folding groupsA group folds with a one-line summary of its values and stays open or folded as the owner left it.
Destructive actionsA plain row or text button, confirmed in a dialog naming what goes (see Confirmation dialog and Undo or confirm); the dialog's confirming button is in error color when it can't be taken back. The confirming button is always a text button in error color, on the app and on the web page; never a red filled button.
WordingPlain sentences, sentence case, no jargon: “Connect a device”, “Push notifications are on”. Producers you own are “Yours”. The person running the server is “the host”. Settings reads “Settings › Sign in a browser”, never “Settings › Devices › Sign in a browser”. A sample build reads “SignalHub 3.4.0 · commit a1b2c3d”. About this server shows it as “Server: SignalHub 3.4.0 · commit a1b2c3d” next to the app's own “This app: …” line (on the web, “This page: …”). Needs a server change (queued with the design lock-in).
SecretsShown once, in monospace, with a copy action and a sentence saying it will not be shown again; a key's screen offers Copy and close; Copied stays on it while it is open.
StatusSaid in words next to the control (“Push notifications are on”), not only by color.
RolesA role is said by a section and its one-sentence explanation, or by a tag whose form differs; the app shows what a role can do and hides what it cannot, or says who can help (“Ask an admin of this server.”).
ErrorsA field error under the field; a failed change a snackbar with Retry; a list that failed a banner or an empty state with Try again; a missing thing the full-screen “not available” state. Each says what happened and what to do.

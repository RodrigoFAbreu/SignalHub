1Status: is SignalHub working?

Shell A, one version. The page answers the question in its first line, in words and an icon (SignalHub is working, or SignalHub needs attention), never by colour alone. Below it the parts are in plain language, each with a value and one line on what to do when it is wrong; the problem rows move to the top under their own heading with a red edge, the Needs attention word and a warning icon. There is no list and no side pane: Status is one column of answers, so the page uses the width for readable lines instead. Raw health check names, values and the endpoints they come from are only in the Technical details fold at the end. Nothing here can be changed (settings live in the server's .env and need a restart), and the page says so. It reads /q/info, /q/health, /api/v1/admin/status, the device list and the newest event, and looks again every 30 seconds while it is open. Sample data only.

First line: the answer. Then three groups in the order an operator asks: is it delivering (database, push service, the two backlogs, devices that failed), what happened lately (last event, last push) and which server is this (version, running since, retention). A row with a chip has a judgement (Working or Needs attention); an informational row has none. The revision is the first seven characters of signalhub.revision; the whole value is in Technical details. Retention appears only when it is set. Each “If it goes wrong” line is one sentence naming the setting or place to look, never a log. Refresh is the icon in the header; the page also looks again by itself. The rail's status button follows the one rule written in the shell page's note.

Accessible names. Landmarks: the rail is a navigation named “Sections” and the page is the main region. Headings: “Status” is the level 1 heading, the answer (“SignalHub is working”) is level 2 and each group (Delivering events, Activity, This server) is level 3. Each row is a list item whose name is the part and its state, never colour alone. Icon buttons have names (“Refresh the status”). The values refresh by themselves and are announced politely only when the answer changes.

The same page with a failing push service. The headline changes to “SignalHub needs attention” with a warning icon and says what still works (events are received and stored) and how many things to look at; each is a chip that scrolls to its row. The problem rows sit first, under a red heading with an icon, each with a red edge, an error icon and the words Needs attention, so colour is never the only cue. The rail's status button shows the same (a warning icon and the word Check), by the one rule written in the shell page's note. The row Events waiting to be pushed (events stored whose push has not been handed to the push service yet) stays Working here (0 events waiting). Both rows under Needs attention follow the rules below; the Devices row is a row warning, not part of the headline.

When the page says Needs attention. Any one of: the database check is down; no push service is set up; every device that has a push address failed its last push, with at least one such device (the push service is likely down); the events waiting to be pushed are above 20 and have not fallen over two checks in a row; pushes were given up since this page opened (the page remembers the count it saw when it opened: it is not a count since the server started); or a part could not be read. A single device's failure is never the headline: it is a row warning (“2 devices' last push failed”) with a link to Devices filtered to Push problems, drawn here under Worth a look. ST2 shows the third rule (3 of 3 devices with a push address failed) and the fifth (12 given up since the page opened).

The fold holds everything the plain-language rows were made from: each endpoint with its raw check names and values, monospaced, so an operator can match them to a log, a monitor or a bug report.

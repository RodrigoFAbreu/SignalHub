1Sign in with the admin token: the first screen, before the shell

The only screen without the rail. There are no passwords and no accounts here: the operator pastes the admin token (SIGNALHUB_ADMIN_TOKEN from the server's .env) and the page checks it with the management API. The screen says what the page is, that it is served only on the server's own port (it is not reachable through the public address), and, plainly, that the token stays in this page only: it is kept in the page's memory, never in the browser's storage or a cookie, so reloading or closing the tab asks again. One column, one field, one button; the field has a show and hide toggle (48 px target) and a minimum of 32 characters, which keeps Sign in off until it is met. Seven states, dark, one version. Sample data only.

Accessible names. This screen is the main region of the page; “SignalHub admin” is its level 1 heading. The field is labelled “Admin token” and its help line is its description. The eye is a 48 px toggle button named “Show the token” or “Hide the token”. An error message is announced as soon as it appears.

Try again

A network failure, a timeout or an address with no server there. The token is kept in the field, and the button says Try again. Any other answer from the server (500, 502, 503) reads the same way with its number: “SignalHub answered 503. Try again; if it stays, read the server's log.”

Sign in

Any management request that answers 401 sends the page here. The section and the selected item stay in the address (#events/…), so the next sign-in returns to the same place and the older list is not shown (it came from a token that no longer works). It is neutral, not red: nothing the operator typed was wrong. A change that was in flight (a rename, a revoke) is not repeated; the page does not know if it went through, and the screen after sign-in shows the real state.

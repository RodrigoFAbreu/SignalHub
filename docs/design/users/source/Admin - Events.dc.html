1Events options: three ways to browse, find and act

The shell is fixed (option A, rail and detail pane, chosen by the owner on 2026-10-11) and so is the data: the API lists events newest first by cursor, 25 at a time, filtered by producer, severity and category (each with several values at once), user (and whether it owns or subscribes), read state and received date (from, before); it has no text search, no sort and no total. Each option answers “browse a stream with many events, find what went wrong, act on many events” differently, on 1440 px with the same event (Build 1842 failed on main) selected. Recommendation: A. It keeps the Producers table and pane the operator already knows, has the smallest number of new ideas, shows severity, producer and time in aligned columns so a failure stands out by scanning one column, and keeps the pane beside the list so a selection and its pushes are in view together. B reads well for catching up but cannot compare rows or scan a column; C is the strongest for hunting a problem but depends on server counts that do not exist today, and its sheet hides the list. The rest of this section (detail, selection, dialogs, states, phone) is drawn in A, on this page and its companions Admin - Events states.dc.html and Admin - Events dialogs.dc.html; B and C adapt: B moves the same bar and dialogs to its floating bar and panel footer, C keeps them in the header and sidebar. Chosen: A (owner, 2026-10-11). B and C stay as drawn, for the record, with their detail pane shortened.

Layout. Dense table, filter chips and the same fixed 480 px pane as the Producers section; the pane has two tabs, Event and Pushes. Filters: chips in the order of the task: Read state, Severity, Push problems, Producer, Category, User and Received. Producer, Severity and Category choose several values (checkboxes); User and Read state choose one; Received opens a from and before date range with presets; Push problems is on or off. An active chip is filled and shows its value; “Their producers” appears as one more chip only once a user is chosen. The chip row wraps onto a second line when it does not fit, so no chip is hidden. Changing a filter returns to the newest page. Paging: 25 per page with Newer and Older (48 px buttons) at the foot of the table, because the API pages by cursor and has no total or page number (so no “page 3 of 9”). Newer goes back to a page already loaded: the page keeps the cursors of the pages it has shown. The header cells are plain labels (“Received” is not a sort: events always come newest first). The table scrolls inside its frame, the pager stays put. Selection: a checkbox on every row and a header checkbox that selects the 25 on the page; a bar replaces the chips (count, Select all on this page, Mark read, Delete) and Delete asks first. Test event and delete by rule: Send a test event is the tonal button in the header, Delete events by rule is in the header's ⋮ menu (next to Refresh), because it is rare and destructive; its dialog offers presets (older than 30, 90 or 365 days) beside a date. Names and structure: the page title is the h1, the rail is a nav landmark, the table is a grid (one tab stop; arrow keys move between rows, Enter opens a row, Space ticks it), the pane is a region named by the event title with an h2; each row checkbox is named by its event (“Select Build 1842 failed on main”); icon buttons are named (Refresh, More, Close). 1280: the pane is 420 px and the Category column folds into the Severity cell. Below 1180 px: the pane becomes a side sheet over the table, as in the shell's option C.

Needs a server change: a total count (“25 of 1,284”); today the list has none, so the header only says “Newest first”.
Needs a server change (E-OUTCOME): the “Push problems” chip and the marker on a row need each event's push outcome (failed or given up) in the list and a filter by outcome; today the list does not say how an event's pushes went, which the Pushes tab reads one event at a time.

Layout. Events grouped by day (Today, Yesterday, then dates) in two-line rows like the users' inbox, the same fixed pane (drawn here with the same Event tab as A, shortened). The filter panel is collapsed by default behind a Filters button that shows how many are active; open, it holds the filters in a grid (Producer, Severity and Category choose several values; Received is a date range; Push problems needs server item E-OUTCOME). Paging: infinite scroll by cursor: after the 25th row a “Load 25 older events” row loads the next chunk when it scrolls into view (the button is the keyboard and error fallback, and the scroll position is kept on refresh). Day headers show how many of the loaded events fall on that day, not a total. Selection: a day header's checkbox selects that day's loaded events; rows get a checkbox on hover or focus (always on touch); the bulk bar floats at the bottom of the list. Test event and delete by rule: Send a test event in the header; Delete events by rule at the foot of the filter panel, where a producer and a date are already one click away.
